# Conformance Coverage Matrix

This matrix tracks the higher-risk IR/runtime surfaces that have repeatedly come up in audit passes. It is not a replacement for the case list in `README.md`; it maps semantic obligations to representative case files.

## Coverage Basis

Add a conformance case when it isolates a distinct semantic obligation, a previously observed implementation failure mode, or a specified cross-product where the axes can fail independently. Do not add cases only to fill a mechanical matrix. Large families such as generated-trigger replay, `all_ops` reentrancy, and multiple-effect ordering are retained only where the source context, target-resolution phase, child-model boundary, or error/replay ordering changes the runtime contract.

## Known Expressiveness Limits

| Gap | Status |
| --- | --- |
| Snapshot queued/recently processed event entries | Not currently isolated; current snapshot assertions cover selectable current-state event details and queue length, and behavior/script steps cannot pause with a regular event pending in the runtime queue before it is popped. |
| Snapshot completion and exit-point event details before internal production | Not yet covered; current script steps cannot pause between final/exit-point event production and handling to observe those transient selectable events. |
| Behavior-side operation call payloads | Not currently expressible; behavior `call` ops take an operation name but no payload/data operand, so child behavior-call-data variants cannot be represented without extending the IR schema/runner contract. |
| Child operation-body payload capture via script/API call | Not currently isolated; script/API `call` resolves operation bodies on the runtime instance model, while child `on_call` payload routing is covered separately. |
| Malformed script-step validation | Not yet covered; the case schema permits malformed runtime script steps, but the shared runner contract does not define validation-mode script error codes or whether malformed scripts are model-validation cases. |
| Group single-member cardinality | Spec wording is inconsistent: `MakeGroup(machines...)` parameters say two or more machines, while constraints say at least one. No conformance case should assert either behavior until the DSL resolves this. |
| Sibling activity progress after parent submachine exit | Not currently isolated; the portable activity ops can prove cancellation/prevented late progress for the exited child, but they cannot deterministically force only a sibling child activity to resume after another parent instance exits its submachine boundary. |
